# Curriculum map — approved Module A revision

v12 implements the user-approved operational scope. The sequence retains the completed pipeline and experiment activities.

| ID | Type / topic | Exact approved outcome |
|---|---|---|
| A-S1-01 | Concept Note: From notebook to pipeline | Explain why a reproducible training/inference pipeline replaces a one-off notebook workflow, and identify the 5 stages a production ML pipeline must cover - ingestion, preprocessing, training, evaluation, inference. |
| A-S1-02 | Practical Walkthrough: Reading the provided pipeline scaffold | Trace how data moves through the provided training/inference pipeline scaffold from raw input to served prediction, and label each stage's purpose. |
| A-S1-03 | Practical Walkthrough: Adding and validating a bounded pipeline stage | Follow an expert adding one preprocessing or validation stage to the provided pipeline, then verify its input/output contract and confirm that the unchanged stages still run. |
| A-S1-04 | Independent Practice: Explain-the-code checkpoint | Given an AI-generated addition to the pipeline, explain line by line what it does, test its input/output contract, and identify any part that needs correction before merging. |
| A-S1-05 | Concept Note: Batch vs real-time inference tradeoffs | Compare batch and real-time inference patterns - latency, cost, throughput - and justify which pattern the provided inference brief requires. |
| A-S1-06 | Assessment Lesson: Pipeline extension deliverable | Deliverable: the provided pipeline scaffold extended with at least 1 validated stage, a line-by-line explanation of the changed logic, and a justified batch-vs-real-time recommendation for the inference brief. |
| A-S2-01 | Concept Note: Why ad hoc tracking breaks down at scale | Identify 3+ failure modes of tracking experiments manually (spreadsheets, notebook print statements) once a team runs many models, and explain why systematic tracking matters for auditability. |
| A-S2-02 | Concept Note: Controls, confounders, and decision metrics | Explain why a run comparison is invalid when dataset split, evaluation conditions, or multiple uncontrolled factors change, and distinguish a primary decision metric from diagnostic metrics. |
| A-S2-03 | Independent Practice: Building the five-run experiment matrix | Define a five-run experiment matrix for the provided training and inference pipeline starter that holds the dataset split and evaluation conditions constant, names the factor varied in each comparison, selects a primary metric tied to the inference brief, and labels any run that is not directly comparable. |
| A-S2-04 | Practical Walkthrough: Revisiting MLflow in a pipeline context | Use the provided MLflow setup to log parameters, metrics, and artifacts automatically as part of the cumulative pipeline, building on basic experiment logging from T4 (AI track). |
| A-S2-05 | Independent Practice: Comparing multiple runs systematically | Use the MLflow UI to compare 5+ experiment runs against each other and identify the best-performing configuration for a given metric. |
| A-S2-06 | Independent Practice: Autologging and reducing manual tracking overhead | Configure autologging for the pipeline and explain the tradeoff between autologging convenience and control over what gets logged. |
| A-S2-07 | Practical Walkthrough: Validating an assistant-generated experiment summary | Direct an approved assistant to generate a summary comparison across logged experiment runs, validate every recommendation against the raw MLflow data and the declared primary metric, and flag any inaccuracy or invalid comparison. |
| A-S2-08 | Assessment Lesson: Experiment tracking deliverable | Deliverable: at least 5 experiment configurations logged and compared in MLflow, an autologging setup, and an AI-assisted summary recommending which configuration to promote - with the summary validated against raw data. |
| A-S3-01 | Concept Note: From "which file is production?" to a registry | Explain 3 problems a model registry solves that ad hoc file-saving does not - versioning, alias/tag-based lifecycle control, and auditability - and recognise staging, production, and archived as superseded stage vocabulary replaced by aliases, tags, and environment-specific registered models. |
| A-S3-02 | Practical Walkthrough: Registering and promoting a model | Use the provided model registry scaffold to register a new model version, record its validation status with tags, and promote it by assigning the scaffold's active-model alias. |
| A-S3-03 | Concept Note: Recognising drift and choosing a response | Distinguish data drift, prediction drift and measured performance degradation; compare model drift with prompt or behavior drift; and justify investigation, re-evaluation or retraining from the available evidence. |
| A-S3-04 | Practical Walkthrough: From a monitoring signal to an evaluated candidate | Use the provided statistical monitoring scaffold to compare reference and current inference data with one pinned model, apply a declared signal-threshold-action policy, train a candidate only when labeled evidence justifies it, and compare incumbent and candidate on the same separate validation rows. |
| A-S3-05 | Independent Practice: Rolling back a bad model version | Apply a declared feedback policy to unfamiliar monitoring evidence, retain or qualify a retrained candidate using separate validation data, and restore a suitable previously approved active version in a supplied rollback incident, documenting the resulting audit and new inference evidence. |
| A-S3-06 | Assessment Lesson: Registry lifecycle deliverable | Deliverable: a registered and validated active model, an evidence-backed drift and re-evaluation or retraining decision with its signal, threshold and action, a candidate comparison on separate validation rows, and a demonstrated rollback with audit and fresh inference evidence. |
| A-S4-01 | Concept Note: What full reproducibility requires | Identify the code version, data snapshot, parameters/configuration, environment, and model artifact that must be traceable together for a training run to be reproducible, including the feedback dataset used by an operational response. |
| A-S4-02 | Independent Practice: Integrating pipeline, tracking, and registry | Scope the remaining handoff work, connect pipeline, tracking, registry and operational-response evidence, then replay the selected run from its recorded source, data, configuration and environment within the declared result tolerance. |
| A-S4-03 | Independent Practice: Proving the selected serving path uses the active version | Exercise a bounded drift-trigger-response cycle in the cumulative system, justify the response using the declared policy, and verify that a fresh inference job uses the resulting intended active model version and meets the inference brief. |
| A-S4-04 | Independent Practice: Setup, run, and expected-evidence instructions | Produce reproducible setup and run instructions naming the selected recipe and expected receiving evidence, plus a short incident record linking an observed trigger, affected version, timeline, response, verified resulting state and one owned follow-up action. |
| A-S4-05 | Independent Practice: Proving the pipeline reproduces | Re-run the completed pipeline from the declared clean state, verify its lineage and result against the tolerance declared in the clean-state verification specification, and document and diagnose any divergence. |
| A-S4-06 | Assessment Lesson: Reproducible pipeline deliverable | Deliverable: the cumulative pipeline reproduced from the declared clean state with traceable code/data/configuration/environment/model lineage, reproducible setup/run instructions and an explained extension, plus one evidenced drift-trigger-retraining or recovery cycle, fresh active-version inference evidence, and a short incident record with a follow-up action. |

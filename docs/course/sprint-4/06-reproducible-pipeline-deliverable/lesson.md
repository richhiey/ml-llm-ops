# Reproducible pipeline deliverable

Harbor Facilities receives your cumulative operational pipeline. The recipient needs to inspect why a model was selected, rebuild that exact recipe and recognise an unfamiliar receiving failure. Existing good evidence can be reused when its source and conditions still match.

## What you will work with

Continue the same project and preserve the original five-run selection, explained extension and lifecycle evidence. Choose the intended operational version explicitly, with its raw decision evidence. Use the [clean-state contract](https://github.com/richhiey/ml-llm-ops/blob/main/docs/clean-state.md) and [receiving runbook](https://github.com/richhiey/ml-llm-ops/blob/main/docs/recovery.md); the four local notebooks remain optional companions.

## Your task

Deliver one connected handoff containing the explained extension and its distinguishing tests; original experiment comparison; actual registry/active-source chain; and one observed monitoring-trigger-response cycle. The cycle needs a declared policy, an unlabeled observation, separate labeled evidence where retraining is justified, candidate evaluation on disjoint validation rows, and the resulting selection or recovery. Explain a drift-without-retraining alternative so an alert cannot be mistaken for permission to train.

Include the short incident record in the same handoff. Its signal, threshold and affected version must agree with raw reports; its timeline must distinguish detection, response and verification. State containment or unresolved conditions honestly. Name one follow-up owner and an observable success check.

Use your validated application release descriptor to export the exact intended run with its fitted artifact and actual training snapshot into `work/handoff-export`. Reuse a canonical export only if its source/data/configuration still match the intended release. If your package is elsewhere, provide that actual canonical path to the intake setup. Restore source into a new folder, install the recorded Python patch and locked environment, and use a new store while the original store is unavailable. Preserve the documented reversible isolation/restoration procedure. Independently inspect matching code/data/configuration/environment, validation RMSE delta at most `0.000001` kWh, and `24` finite ordered predictions within `60` seconds. Record new run/version IDs. A replay in the original environment does not satisfy this receiving boundary.

## Diagnose an unfamiliar damaged receiving copy

The exercise intake supplies `work/receiving-review/brief.txt` and a `candidate-bundle/` received copy of your actual release export. The copy has a bounded unfamiliar receiving fault; the canonical export remains intact. Use the [intake setup reference](https://github.com/richhiey/ml-llm-ops/blob/main/docs/course/exercises/README.md) if the incoming package has not been provisioned. Case preparation belongs to exercise setup, outside the application runtime. Your task begins with inspecting the received package, not manufacturing a failure.

Read the supplied brief and preserve the first failure. Diagnose the earliest failing layer before editing. Repair the copied package from the canonical export without changing its checksum index, model selection, thresholds or tolerance. Explain when earlier receiving evidence remains applicable and when a fresh execution is necessary. Keep the canonical export and original store intact.

## Final check

The inference evidence must be from the resulting intended version. The incident must describe your observed response, not the guided reference fixture or an invented learner request. Reproduction data must be the selected run's snapshot, including feedback when applicable. Take any separate reserved final observation only after the relevant configuration/selection decisions are fixed; never use it to tune the response or claim current-condition quality from historical rows.

# Monitor inputs and evaluate a bounded response

Monitoring reads explicit reference/current cohorts and an explicit policy. It pins the active model for both distributions. An optional independent labeled snapshot supplies validation error. A signal writes observations; it never changes the selected model.

## Inputs and policy

The [provided synthetic cohorts](https://github.com/richhiey/ml-llm-ops/tree/main/docs/course/exercises/monitoring) are separate input assets, not generated by application runtime. Each Linden/Harbor directory contains `reference.csv`, `stable.csv`, `current.csv`, `feedback.csv`, `shift-feedback.csv`, `policy.json` and `data-card.json`. Inspect hashes and units in its card. Reference/current each have `192` independent identifiers. Stable copies reference features with new IDs as an exact control, not a measured false-alarm rate. Current temperature is shifted by `8` degrees Celsius. Each labeled snapshot has `168` train, `48` validation and `24` reserved final rows; its IDs are independent from monitoring cohorts. Feedback simulates an intercept shift; shift-feedback retains the original output law. These constructed cohorts establish no real production chronology or calibrated alert rate.

Policy uses Wasserstein distances in feature units, with default boundaries `3` degrees Celsius, `3` hours, `8` occupancy percentage points and `5` predicted kWh. It requires `96` monitoring rows and `32` labeled validation rows. Labeled RMSE over `3` kWh permits a candidate; acceptance requires candidate RMSE `<=3` kWh and improvement `>=0.5` kWh on the same validation IDs. These are declared example policies, not universal operating recommendations.

## Invoke the actual application API

After explicitly selecting an approved active version, use the same store and actual paths in an ordinary script:

```python
from pathlib import Path
from linden_mlops import Workspace
from linden_mlops.operations import monitor

workspace = Workspace("work/tracking")
inputs = Path("docs/course/exercises/monitoring/linden")
report = monitor(workspace, inputs / "reference.csv", inputs / "current.csv",
                 inputs / "policy.json", "work/operations/labeled-observation.json",
                 feedback_path=inputs / "feedback.csv")
print(report)
```

The report records the pinned version/source run, actual distance/error values, cohort hashes/counts, policy and proposed action. Inspect it before deciding. Small windows return `collect_more`; unlabeled or still-accurate drift returns `investigate`; confirmed degradation may permit a candidate even when distance checks miss it. No final rows supply these decisions.

| Operation | Explicit inputs and observed result |
|---|---|
| `monitor(ws, reference_path, current_path, policy_path, destination, feedback_path=None)` | One pinned model; new observation JSON and retained MLflow evidence |
| `train_candidate(ws, report_path, feedback_path, alpha=1.0)` | Unchanged observed trigger/model/feedback; new actual pending run/version |
| `compare_candidate(ws, report_path, feedback_path, version, destination)` | Incumbent/candidate error on identical independent validation IDs |
| `promote_candidate(ws, comparison_path, reason)` | Rechecks observations, data, models, policy and active state before explicit approved change |
| `write_incident(ws, report_path, comparison_path, destination, explanation, follow_up, batch_name="response-batch")` | Records actual resulting version and fresh completed job plus operator reasoning |

Training a candidate does not activate it. Keep failed candidates and compare raw records before selecting. `promote_candidate` recalculates acceptance; changing a local `passed` Boolean cannot authorize it. A suitable previous approved version can be selected with `activate` for an actual rollback. Do not promote a known failed model just to manufacture an incident.

After a decision, invoke `batch_predict` with a new output name and inspect the actual resolved version, run ID, input sequence and finite output. Existing names refuse overwrite. For rollback, use another name such as `rollback-batch` and supply that name to `write_incident`. The incident requires the job to follow the comparison and match the resulting model. Its checker verifies observations, not the quality of your explanation or follow-up.

## Release the intended operational model

The original experiment selection remains historical after a justified feedback response. Inspect the actual active version and its source run. Create a real release descriptor and consume it:

```sh
uv run linden-mlops export --release work/release.json --destination work/operational-export
```

The descriptor names `model_name`, `version`, `run_id` and `batch_name`; the [API reference](https://github.com/richhiey/ml-llm-ops/blob/main/docs/api-reference.md) defines its active/approved-model, actual-job and source-agreement checks. The separate explicit `--state ACTUAL_STORE --run-id ACTUAL_RUN_ID` route is available for archiving a named run's recipe. It does not perform those release checks and cannot replace evidence that the intended operational model was actually served. Export has no implicit historical-selection default. The exact selected training snapshot is indexed, so feedback-trained recovery uses feedback bytes rather than substituting the original demand data.

Keep policy/monitor/comparison/incident records and the runbook beside the indexed export. [Receiving proof](https://github.com/richhiey/ml-llm-ops/blob/main/docs/recovery.md) uses restored source, exact environment and a new store with producer storage unavailable. Neither original nor feedback final rows may influence candidate selection. Local approval/audit helpers are not a tamper-proof multi-user control plane.
